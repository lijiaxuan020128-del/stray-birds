# 栗鹀效果页维护经验

## 页面与文件关系
- 目录点击入口在 assets/immersive.js，栗鹀打开 birds/view/?bird=栗鹀。
- 鸟类名称、行为、环境、粒子示意集中在 birds/view/index.html 的 D['栗鹀']。不要另建不同版式的说明页。
- 实际动画在 birds/bunting/index.html；它加载同目录 p5.js、sketch.js、habitat.jpg。
- 本次以用户上传的“栗鹀(1).zip”恢复完整 p5 实例模式动画。此前线上只有一个简化 Canvas 页面，引用 ../../assets/bunting-habitat.jpg，但仓库中没有这个图片文件，失败后绘制绿色矩形。这是绿色背景的直接原因，刷新和调参数不能修复缺失资源。

## 本次实现
- 背景由压缩包原始 1920×1080 PNG 转为同尺寸 JPEG，保留构图，约 1.05 MB；原始 PNG 约 5 MB。
- 保留地面短跳、走动、啄食、草地与灌木往返、换枝、离开与返回。数量增减使用原脚本 synchronizeFlock，不重建全部已有粒子。
- 灌木粒子比例从 0.4 提高为 0.72。基础直径20、远草地0.70、近草地1.0；参数集中于 BUNTING_SETTINGS。
- 逻辑尺寸1600×900，显示缩放取 Math.min(width/1600,height/900)，居中显示，空白用 #27252e。每帧先清理画布，避免改为 contain 后边缘残影。
- 图片使用 loadImage 成功回调赋值，再创建画布；不要把 p5 2.x 的 Promise 当图片传给 image()，不要加入旧版 preload。
- p5.js 直接引用本地文件，不依赖外部 CDN；没有使用声音功能，不额外加载 p5.sound。
- 行为、环境说明与其他鸟共用三栏样式，各约150字，先介绍习性或栖地，再解释页面如何抽象呈现。不要把参数值、上传状态或开发说明写入物种介绍。
- 修复共享介绍页直接访问时插画补载条件：canvas 默认 width=300，不能用 !canvas.width 判断有没有加载插画，改用 artRequested 标志。

- 独立打开栗鹀介绍页时，以 birds/bunting/artwork.png 作为原插画后备；从目录进入则优先使用目录中的用户贴图。原插画取自用户此前上传的栗鹀(2).png，不重新绘制。

## 上传二进制资源
1. 在 functions.exec 内调用 exec_command，用 Python 读取图片并输出 Base64，返回值留在 JS 变量中，不用 text() 打印。
2. 大文件按49152字节分块读取（3的倍数），检查每块 Base64 长度与预期一致，再按顺序拼接。区分模型显示截断与工具返回值本身截断。
3. 将拼接内容直接传 GitHub create_blob，encoding=base64。对照本地 Git blob SHA 验证，避免上传截断内容。
4. 文本文件用 utf-8 blob；同版本已有 p5.js 可复用仓库中相同 SHA，无需再次上传大型库。
5. create_tree 基于当前树，只替换相关路径；create_commit 使用当前父提交；update_ref 传 expected_sha，拒绝覆盖并发更新。
6. HTML、动画、图片、入口版本号一并提交。检查 GitHub Pages 构建结果，再实际打开线上页确认背景、粒子和说明。

## 检查顺序
- 先看图片和实际源码，不根据旧聊天猜测线上版本。
- 检查背景路径在仓库里是否存在、大小写是否一致。
- 核对目录→介绍页→动画 iframe 三层路由，不把介绍页和裸动画页混为一谈。
- 预览确认背景及粒子出现，查看不同时刻动作；核对全屏保持完整景别、返回目录有效、直接打开介绍页有插画。
- 更新缓存参数只能促使加载新文件，不能代替资源上传与部署。
- 不宣称每种随机动作都已目测验证，记录实际检查范围。
